# 🧠 Mini NPU 시뮬레이터 (E1-3)

> AI가 이미지를 보는 방식의 핵심인 **MAC(Multiply-Accumulate) 연산**을 NumPy 없이 반복문으로 직접 구현하고,
> 3×3부터 25×25까지 패턴(십자가 / X)을 판별하며 **연산 시간이 N²로 늘어나는 것**을 직접 측정하는 Python 콘솔 프로그램입니다.
> 이 문서만 읽어도 *무엇을, 왜, 어떻게 만들고, 어떤 결과가 나왔는지* 순서대로 이해할 수 있게 정리했습니다.

## 2. data.json 안내 (꼭 읽어주세요)
> **정직 공지:** 과제 PDF에는 `data.json` *파일은 들어 있지 않고* 구조 설명만 있습니다. 그래서 설명된 구조를 그대로 따르는 데이터를
> `tools/make_data.py`(시드 고정)로 직접 만들었습니다. 공식 `data.json`이 따로 있다면 **같은 이름으로 덮어써도 동작**하도록,
> 키/라벨 표기는 설명서 기준(`size_N`, `size_{N}_{idx}`, `input`, `expected`, `cross`/`x`, `+`/`x`)으로 읽고 대소문자·공백 차이는 흡수합니다.

```json
{
  "filters":  { "size_5": {"cross": [[...]], "x": [[...]]}, "size_13": {...}, "size_25": {...} },
  "patterns": { "size_5_1": {"input": [[...]], "expected": "+"}, "size_5_2": {"input": [[...]], "expected": "x"}, ... }
}
```
| 키 | 의미 | 규칙 |
|---|---|---|
| `filters.size_N` | N×N 필터 한 쌍 | 키에서 N을 읽고, 내부 `cross`/`x` 행렬 크기가 N×N인지 검증 |
| `patterns.size_{N}_{idx}` | N×N 패턴 케이스 | **키에서 N을 추출해 `size_N` 필터를 선택**, `input` 크기가 N×N인지 검증 |
| `expected` | 정답 라벨 | `'+'`→Cross, `'x'`→X 로 정규화 후 비교 |

**내가 만든 data.json 구성 (14케이스):** 크기 5/13/25마다 ① 깨끗한 십자가 ② 깨끗한 X ③ 2칸 노이즈 십자가 ④ 2칸 노이즈 X = **12개 정상 케이스**,
그리고 경계 사례 2개 — `size_5_5`(부동소수점 오차 동점), `size_13_5`(모두 1인 패턴, 정확한 동점). 이 2개는 **일부러 FAIL이 나오도록 넣은 것**이고 이유는 5장에서 분석합니다.
스키마 오류(크기 불일치, 라벨 오류 등)는 별도 파일 [`tests/fixtures/data_invalid.json`](tests/fixtures/data_invalid.json)에 모아 두었습니다.

## 3. 구현 요약
### 3.1 파일 구조와 역할

| `tests/` | 단위/통합 테스트 19개 + 오류 데이터 fixture |

### 3.2 실행 흐름
```text
python main.py
   │
   ├─ 모드 1 ── 필터 A 입력 → 필터 B 입력 → 저장 확인 → 패턴 입력
   │            → MAC(A), MAC(B) → |A-B| < 1e-9 ? 판정 불가 : A/B 판정 → 3×3 성능 표
   │            (줄마다 열 개수·숫자 검증, 틀리면 안내 후 '그 줄만' 재입력)
   │
   └─ 모드 2 ── data.json 읽기 ─ 실패하면 안내 후 종료(트레이스백 없음)
                → filters 로드(라벨 정규화, N×N 검증)
                → patterns 순회: 키에서 N 추출 → size_N 필터 선택 → 크기 검증
                                 → MAC(Cross), MAC(X) → epsilon 판정 → expected와 비교 → PASS/FAIL
                                 (케이스 하나가 잘못돼도 그 케이스만 FAIL, 나머지 계속)
                → 성능 분석(3×3, 5×5, 13×13, 25×25) → 총/통과/실패 요약
```

### 3.3 핵심 구현 세 가지
1. **라벨 정규화 (`labels.py`)** — 같은 뜻의 표기(`'+'`, `'cross'`, `'x'`, 대소문자/공백 차이)를 입구에서 표준 라벨 **`Cross`, `X`** 두 개로 통일합니다. 이후 비교·출력·필터 선택은 모두 표준 라벨 기준입니다.
2. **MAC 연산 (`core.py: mac`)** — 이중 `for`로 같은 위치끼리 곱하고(Multiply) 변수에 계속 더합니다(Accumulate). 외부 라이브러리 없이 반복문만 쓰며, 결과는 `float`입니다. N×N이면 곱셈·덧셈이 각각 N²번입니다.
3. **동점 정책 (`core.py: is_tie / judge`)** — 점수를 `==`로 비교하지 않고 `abs(a - b) < 1e-9`이면 **동점**으로 봅니다. 동점이면 `UNDECIDED`(모드 1에서는 "판정 불가")를 출력하고, 기대값(Cross/X)과 다르므로 PASS가 아니라 **FAIL**로 기록합니다.

### 5.2 실패 원인 분석 — "왜 이 2건이 FAIL인가"
실패 원인은 **데이터/스키마 문제 · 로직 문제 · 수치 비교 문제** 세 갈래로 나눠 진단했습니다.

| 케이스 | Cross 점수 | X 점수 | 원인 분류 | 진단 |
|---|---|---|---|---|
| `size_5_5` | 0.30000000000000004 | 0.3 | **수치 비교 (부동소수점)** | 십자가 전용 칸 0.1 + 0.2 와 X 전용 칸 0.3 은 수학적으로 같은 값이지만, 컴퓨터는 이진수로 저장하므로 `0.1 + 0.2 = 0.30000000000000004`가 됩니다. 차이는 약 5.55e-17로 허용오차 1e-9보다 훨씬 작아 **동점**이고, 기대값(Cross)과 달라 FAIL |
| `size_13_5` | 25.0 | 25.0 | **수치 비교 (정확한 동점)** | 모두 1인 패턴은 Cross 필터(1이 25칸)와 X 필터(1이 25칸)에서 점수가 정확히 같습니다. 정보가 없어 구분할 수 없으므로 판정 불가가 올바른 답이고, 기대값이 X라 FAIL |

- **데이터/스키마 문제는 아닙니다.** 두 케이스 모두 키·크기·라벨이 정상이라 로더를 통과했고 점수까지 계산됐습니다.
- **로직 문제도 아닙니다.** 나머지 12케이스는 Cross·X를 정확히 판별했고(노이즈 2칸 포함), 같은 코드가 두 경계 케이스에서는 **의도대로** 동점을 드러냈습니다.
- 즉 이 FAIL은 버그가 아니라 **"동점은 억지로 한쪽을 고르지 않고 판정 불가로 처리한다"는 정책의 결과**입니다.

**정규화와 epsilon을 빼면 어떻게 되는가 (같은 data.json, [`tools/ablation.py`](tools/ablation.py) 실행 결과):**
```text
{{ABLATION}}
```
- **A(정책 없음)** 은 14건 전부 FAIL입니다. 판정은 맞는데 `'+'`와 `'Cross'`, `'x'`와 `'X'`가 문자열로 달라서입니다 → *정규화가 필요한 이유*.
- **B(정규화만)** 는 FAIL 0건이라 좋아 보이지만, 동점 2건을 `>` 비교로 **우연히 한쪽에 찍어 맞춘 것**입니다. 특히 `size_5_5`는 `0.30000000000000004 > 0.3`이라는 계산 오차가 정답처럼 보이게 만든 경우입니다. 합산 순서가 바뀌면 결과가 뒤집힐 수 있어 *믿을 수 없는 통과*입니다 → *epsilon이 필요한 이유*.
- **C(정규화 + epsilon)** 만 동점 2건을 정직하게 드러냅니다.

### 5.3 스키마/데이터 오류 처리 결과 (`data_invalid.json`)
9케이스 중 정상 1건만 PASS, **나머지 8건은 모두 `데이터/스키마`로 분류돼 FAIL이며 프로그램은 한 번도 중단되지 않았습니다.**

### 5.4 성능 분석과 시간 복잡도 O(N²)
같은 크기마다 MAC 1회를 **10번 반복 측정한 평균**입니다. 입력/출력/파일 읽기는 제외하고 `mac()` 호출 구간만 `time.perf_counter()`로 쟀습니다. (모드 2 실행 결과)
```text
{{PERF}}
```
{{PERF_DERIVED}}

**해석 (측정값 기반):**
1. 이중 반복문은 바깥 N번 × 안쪽 N번 = **N²번** 곱셈·덧셈을 합니다. 표의 "연산 횟수(N²)" 열이 이 값이며 3×3은 9번, 25×25는 625번입니다.
2. 크기를 3에서 25로 키우면 연산 횟수는 **{{OPS_3_25}}배**(9 → 625)가 되고, 측정 시간은 **{{TIME_3_25}}배**가 됐습니다.
3. 13×13에서 25×25로 키울 때는 연산 횟수가 **{{OPS_13_25}}배**인데 측정 시간은 **{{TIME_13_25}}배**입니다. 만약 O(N)이라면 약 {{LIN_13_25}}배, O(N³)이라면 약 {{CUB_13_25}}배가 나왔어야 하므로 **O(N²) 예측에 가장 가깝습니다.**
4. 3×3 근처에서 배율이 연산 횟수 배율보다 작은 이유는 **연산 횟수와 무관한 고정 비용**(함수 호출, 반복문 준비, 타이머 호출) 때문입니다. 연산이 적을수록 이 고정 비용이 큰 비중을 차지해 "연산 1번당 시간"이 크게 나옵니다(표의 마지막 열: {{NS_3}} ns → {{NS_25}} ns).
5. 크기가 커질수록 고정 비용 비중이 줄어 연산당 시간이 일정한 값에 가까워지고, 그때 **전체 시간 ≈ (연산당 시간) × N²** 이 됩니다. 이것이 시간 복잡도 O(N²)의 의미입니다.
6. 한 번만 재면 OS 스케줄링·캐시 상태에 따라 값이 흔들리기 때문에 10회 평균을 썼습니다. 그래도 실행마다 소수 셋째 자리 정도는 달라질 수 있어, **절대값보다 배율과 경향**을 근거로 봐야 합니다.
7. 실제 AI 모델은 수백×수백 필터를 수천 개 쓰므로 N²의 곱셈이 폭발적으로 늘어납니다. CPU는 이것을 하나씩 순서대로 처리(직렬)하지만 **NPU는 이 MAC들을 한꺼번에 병렬 처리**하도록 만든 칩입니다. 이 시뮬레이터에서 측정한 "N²로 늘어나는 시간"이 바로 NPU가 필요한 이유입니다.
8. 한계: 이 프로그램은 파이썬 반복문(직렬)으로 계산하므로 NPU의 병렬성은 흉내 낼 수 없고, 연산 **횟수**가 N²로 늘어난다는 사실만 확인할 수 있습니다.

### 5.5 (보너스) 최적화 전/후: 2차원 → 1차원(길이 N²)
`pattern[i][j]` 이중 인덱싱 + 이중 반복문을 길이 N²의 1차원 리스트 + 단일 반복문으로 바꿨습니다. 같은 입력, 같은 반복 횟수(200회)로 비교한 결과입니다. (변환 시간은 제외)
```text
{{OPT}}
```
- 점수는 **모든 크기에서 동일**(결과동일 열)하고 연산 횟수도 N²로 같으므로 *복잡도는 그대로 O(N²)* 이며, 줄어든 것은 반복문 오버헤드와 인덱싱 비용입니다.
- 배율은 작은 크기에서 크고 큰 크기에서 1에 가까워지는 경향이 나왔습니다. 다만 이 값은 **실행마다 흔들리므로** 정확한 배율이 아니라 "1차원이 같거나 조금 빠르다" 정도로 읽어야 합니다. (반복 10회로 한 실행에서는 25×25가 거의 1.0배였던 적도 있습니다.)
- 패턴 생성기(`patterns.py`)는 모드 3, 성능 분석, ablation, 데이터 생성에서 모두 재사용됩니다.

## 7. 과제 목표 자기 점검 (개념 정리)
| 질문 | 내 설명 |
|---|---|
| **MAC이 무엇이고 왜 중요한가** | 같은 위치의 값끼리 곱하고(Multiply) 모두 더하는(Accumulate) 연산입니다. 이미지 인식 같은 AI 계산은 이 단순 연산을 수억 번 반복하므로, MAC을 빠르게 처리하는 것이 곧 AI의 속도입니다. NPU는 이 MAC을 병렬로 처리하는 전용 칩입니다. |
| **패턴과 필터로 유사도(점수)를 계산하는 원리** | 필터는 "찾고 싶은 모양"을 숫자 배열로 적어 둔 기준표입니다. 패턴 위에 필터를 겹쳐 같은 칸끼리 곱해 더하면, 모양이 겹치는 칸이 많을수록 점수가 커집니다. 십자가 입력에 십자가 필터는 5점, X 필터는 1점이었습니다(3×3). |
| **data.json의 키/라벨 규칙과 정규화 이유** | 필터 키는 `size_N`, 패턴 키는 `size_{N}_{idx}`라서 키에서 N을 읽어 맞는 필터를 고릅니다. 라벨은 `'+'`, `'x'`, `'cross'`처럼 표기가 섞여 있어, 내부에서는 `Cross`/`X` 두 개로 통일해야 비교가 일관됩니다. 안 하면 판정이 맞아도 문자열이 달라 FAIL이 납니다(5.2 ablation A). |
| **부동소수점 오차와 epsilon** | 컴퓨터는 소수를 이진수로 근사해 저장해서 `0.1+0.2 ≠ 0.3`이 됩니다. 그래서 `==` 대신 "차이가 1e-9보다 작으면 같다"고 보는 허용오차 정책이 필요합니다. 이 프로젝트의 `size_5_5`가 그 실제 사례입니다. |
| **크기별 시간 측정과 O(N²)** | N을 키우면 연산 횟수가 N²로 늘고, 측정 시간도 그 경향을 따랐습니다(5.4). 고정 비용 때문에 작은 N에서는 배율이 덜 나온다는 점까지 확인했습니다. |
| **실패 원인을 데이터 / 로직 / 수치 비교로 분리** | 로더를 통과했는지(데이터), 다른 케이스가 정상 판정하는지(로직), 점수 차이가 허용오차 안인지(수치)를 순서대로 확인합니다. 5.2에서 두 FAIL은 데이터·로직이 아니라 수치 비교(동점) 정책 때문임을 이렇게 가려냈습니다. |
